# Developing CodeplugMe

Build, test, and internals notes for working on the code. For what the tool does
and how to use it, see the main [`README.md`](../README.md). The design and
roadmap live in [`PLAN.md`](../PLAN.md).

## Layout

- `core/`: the `codeplugme-core` library. Byte transport (real + mock), the
  programming protocol, backup/restore, port enumeration, and the codeplug model
  (channels, zones, scan lists, DMR contacts/talk groups, RX group lists, radio
  IDs, plus read-only APRS and zone A/B) with lossless parse, edit, re-serialize
  and JSON batch editing (`src/anytone/codeplug/edits.rs`). It has two
  host-facing surfaces over the same layers: the C FFI for the macOS app
  (`src/ffi.rs`, header in `core/include/codeplugme_core.h`) and the UniFFI
  surface for the Android app (`src/api.rs`). `src/geo/` is the repeater import.

  Both surfaces are behind features. `desktop` (the default) brings in
  `serialport` and with it `SerialTransport`, port enumeration, and the C ABI.
  `uniffi-api` brings in `src/api.rs`, where the host language supplies the
  transport, because `serialport` needs libudev and Android does not have it.
  Both also enable `net` (`ureq` with rustls) for the repeater downloads. The
  USB identity table lives in `src/usb_ids.rs`, outside both, so the two
  platforms attribute radios from one table.
- `cli/`: the `codeplugme-cli` binary.
- `CodeplugMe/`: the SwiftUI macOS app, linked against the `codeplugme-core`
  staticlib. The Xcode project is generated by XcodeGen from `project.yml` and
  built by `build.sh`.
- `CodeplugMeTests/`: Swift tests for the app layer (formatting, edit-spec
  encoding, and the save/recovery model).
- `android/`: the Jetpack Compose Android app over the same core, talking to the
  radio through the USB host API. See [`android/README.md`](../android/README.md).
- `scripts/gen-bindings.sh`: regenerates the Android Kotlin bindings from
  `core/src/api.rs`. The macOS app keeps its hand-written C header.
- `tools/make-icon.swift`: draws the app icon and writes the asset catalog PNGs.
- `docs/`: memory maps, the repeater import, and the CPS breakage playbook.

## Prerequisites

- Rust stable via `rustup`.
- For the macOS app: Xcode (with `xcodebuild`) and
  [XcodeGen](https://github.com/yonaskolb/XcodeGen) (`brew install xcodegen`).
- For the Android app: the Android SDK and NDK, `cargo-ndk`, and the Android Rust
  targets. See [`android/README.md`](../android/README.md).

## Build and test

```sh
# Rust core + CLI
cargo build
cargo test
cargo clippy --all-targets

# macOS app (builds the Rust staticlib first, then the app; ad-hoc signed)
./build.sh
# → build/Debug/CodeplugMe.app

# Swift app tests
xcodebuild test -project CodeplugMe.xcodeproj -scheme CodeplugMe \
  -destination 'platform=macOS'

# App icon (regenerate after editing the drawing code)
swift tools/make-icon.swift

# Android app
android/build.sh            # debug APK
android/build.sh test       # host JVM tests, no device or radio needed
android/build.sh install    # build and adb install
android/build.sh release    # release APK, unsigned
android/build.sh bindings   # regenerate the Kotlin bindings
android/build.sh clean
```

All protocol and device logic is unit-tested against an in-memory
`MockTransport` that emulates the radio, so the full suite runs with no hardware.
The Swift tests drive the real core against a synthetic all-zero codeplug image.

## Release build

`./build.sh release` produces a universal (arm64 + x86_64) Release build, signed
with a Developer ID certificate and the hardened runtime, packaged as a DMG in
`dist/`.

It picks the first "Developer ID Application" certificate in your keychain, or
set `SIGNING_IDENTITY` to choose one. Without one it falls back to an ad-hoc
signature, which runs on your own machine but is blocked by Gatekeeper elsewhere.

For a DMG that opens cleanly on someone else's Mac you also need notarization.
Store an app-specific password once, then pass the profile name:

```sh
xcrun notarytool store-credentials anytone-notary \
  --apple-id you@example.com --team-id TEAMID --password <app-specific-password>

NOTARY_PROFILE=anytone-notary ./build.sh release
```

Bump `MARKETING_VERSION` in `project.yml` to change the version in the DMG name.

## AnyTone transfer details that are load-bearing

These were all found by testing on real hardware.

- **Sector read-modify-write.** The radio erases flash in 32 KB sectors, so any
  write into a sector erases the whole thing. `write_codeplug` reads every sector
  it will touch, overlays only the modelled blocks, and writes the sector back.
  The history is in [`diagnosing-cps-breakage.md`](diagnosing-cps-breakage.md).
- **The radio-settings region (`0x02500000`-`0x025014FF`) is never written.**
  Writing it once locked a radio behind an unknown power-on password with Chinese
  menus. APRS and zone A/B are shown read-only for this reason.
- The write command must end with a trailing `0x06` byte, or the radio never ACKs.
- Writing every unused slot resets the radio mid-transfer, so only active records
  are written.
- Records must precede the bitmap that references them (ascending address order),
  because the radio commits on program-mode **exit**, not per block.
- For the same reason writes are not read-back verified. An immediate read
  returns the pre-commit value. Each block's ACK is the transfer check, as in the
  vendor CPS and qdmr.

## KT-5000 details

- The write map excludes `0x2000`-`0x23EF` (calibration-looking data) and
  `0x3100`-`0x31FF`, so a codeplug from elsewhere cannot blank them. Restoring
  `0x2000` is an explicit `codeplugme-cli rescue write --address 0x2000`.
- Its USB VID/PID is not known yet. To add auto-detection, run
  `system_profiler SPUSBDataType` with the radio plugged in and add the VID/PID
  to `KNOWN_USB_IDS` in `core/src/ports.rs`. Don't guess one: a wrong ID would
  silently match unrelated USB-serial adapters.
- The settings block is only partly modelled on purpose. The common reference
  driver's map is known-wrong for this model, so unlabelled bytes are preserved.
- Protocol and memory layout: [`qyt-kt5000-memory-map.md`](qyt-kt5000-memory-map.md).

## Manual hardware checks

- `codeplugme-cli info` and the GUI's Identify show the radio's model string.
- GUI Read from Radio produces a `.bin` byte-identical to `codeplugme-cli backup`.
- Writing an unmodified read back to the radio completes cleanly.
- Edit one channel name, write it, and confirm on the radio.
- With one radio plugged in, the Device list shows exactly one row (macOS
  enumerates each serial device as both `cu.` and `tty.`; the core collapses them).
